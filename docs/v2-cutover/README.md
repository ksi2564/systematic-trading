## 소유자 결정 체크리스트

아래 항목으로 C0 범위를 승인하기 전에는 자동 섀도 개발을 시작하지 않는다.
승인 후에는 확정된 범위 안의 개발·테스트·스테이징 증적 생성을 자동 진행할 수 있다.

- [ ] **사용자 승인 필수** — QQQM 기준선의 낙폭 구간, 회복 조건, 목표 비중,
  VIX·200MA 규칙이 원하는 전략이다.
- [ ] **사용자 승인 필수** — 기존처럼 16:15 ET에 EOD 상태를 만들고 다음 거래일
  09:45 ET에 계좌·VIX·200MA로 리밸런싱 의도를 판단하는 두 단계 운용이 맞다.
- [ ] **사용자 승인 필수** — Java와 v2의 상태·목표 비중은 **정확히 일치**해야 하며, 금액·수량 차이는 동일
  입력과 반올림 규칙으로 원인을 설명할 수 있어야 한다.
- [ ] **사용자 승인 필수** — 권장 섀도 관찰 기간 `미국 거래일 20일 연속`과 중대 불일치 `0건` 기준을 채택한다.
- [ ] **사용자 승인 필수** — C0에서 스테이징 QA용 테스트 전략·계좌·연구 run·
  v2 제어 상태·감사 기록의 생성·변경 여부와 종류·건수를 승인한다. 승인 이후에는
  확정된 범위 안에서만 자동으로 변경해도 된다.
- [ ] **사용자 승인 필수** — 실제 KIS 자격증명 입력, 계좌 재개, `LIVE_APPROVED`, 실주문, Java 정지는 본인만
  수행하는 수동 검증으로 남긴다.
- [ ] **사용자 승인 필수** — 실거래 전환 시 첫 계좌, 금액 한도, 시간대는 섀도 결과를 본 뒤 별도로 승인한다.
- [ ] **사용자 승인 필수** — Java 중단, DNS·트래픽 전환, 롤백 확정은 각각 실행 직전에 별도로 승인한다.
- [ ] **사용자 승인 필수** — 전환 실패 시 v2를 먼저 차단하고 미확정 주문을 확인한 뒤 Java로 복귀한다.

## 변하지 않는 안전 원칙

1. 섀도 단계에서는 Java가 유일한 기존 운영 주체다.
2. v2는 공식·완전한 입력이 없으면 계산을 생략하고 이유를 남긴다.
3. 섀도 결과는 `주문 의도`일 뿐 브로커 전송 대상이 아니다.
4. 화면 QA는 실제 주문 없이 끝나야 한다.
5. 실거래 전환은 문서 승인, 섀도 통과, 복구 훈련, 사용자 최종 승인을 모두 요구한다.

## 문서 관리 규칙

- 요구사항 ID는 의미가 바뀌어도 재사용하지 않는다. 폐기 시 `RETIRED`로 남긴다.
- 구현 PR은 관련 요구사항 ID와 QA ID를 본문에 연결한다.
- 화면 문구나 흐름을 바꾸면 `SCREEN_SPEC.md`와 증적 시나리오도 함께 바꾼다.
- 배포 사실은 커밋 SHA, Actions run, 화면 증적이 모두 있을 때만 `완료`로 기록한다.
