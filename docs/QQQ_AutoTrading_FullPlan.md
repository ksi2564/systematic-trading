# QQQ 자동매매 시스템 기획서

기준일: 2026-04-02  
기준: 현재 저장소 코드 (`master`)를 역으로 분석해 도출한 제품/기능 기획서

이 문서는 초기 초안이 아니라, 실제 구현된 시스템을 기준으로 다시 정리한 기획서다. 구현과 맞지 않는 과거 전제나 기술 스택 설명은 제외하고, 현재 시스템이 제공하는 기능과 운영 규칙만 정리한다.

## 1. 제품 정의

이 시스템은 한국투자증권(KIS) Open API와 Yahoo Finance 데이터를 이용해 QQQ, QLD, TQQQ 3개 ETF 포트폴리오를 자동으로 관리하는 백엔드 애플리케이션이다.

핵심 목적은 다음과 같다.

- QQQ 종가 기준 시장 상태를 일별로 계산하고 전략 상태를 저장한다.
- 현재 포트폴리오와 목표 비중의 차이를 바탕으로 리밸런싱 필요 여부를 판단한다.
- 판단 결과를 `ExecutionJob`과 `ExecutionOrder`로 남기고 실제 주문까지 수행한다.
- 운영자는 API와 스케줄러를 통해 전략 계산, 수동 실행, 대시보드 조회를 수행할 수 있다.
- 모든 핵심 결정은 재현 가능한 상태 객체와 실행 이력으로 남는다.

## 2. 대상 사용자와 운영 방식

### 2.1 주요 사용자

- 운영자: 전략 상태 확인, 수동 리밸런싱 실행, 작업 이력 조회, KIS 연동 상태 확인
- 시스템 자체: 스케줄에 따라 EOD 계산과 자동 실행을 수행

### 2.2 운용 방식

- 장 마감 후 QQQ 기준 전략 상태를 계산한다.
- 미국장 개장 후 일정 시점에 자동 리밸런싱을 시도할 수 있다.
- 운영자는 필요 시 수동으로 EOD 계산과 리밸런싱 실행을 트리거할 수 있다.
- 실제 주문 실행은 `trading.execution.enabled`와 Kill Switch 상태를 모두 통과해야 한다.

## 3. 핵심 비즈니스 규칙

### 3.1 운용 대상 자산

- QQQ
- QLD
- TQQQ

### 3.2 전략 상태 계산

전략 상태는 `StrategyState`로 관리하며, 주요 필드는 다음과 같다.

- 기준 일자 `asOfDate`
- 전고점 종가 `ath`
- 최근 종가 `lastClose`
- 현재 낙폭 `drawdownPct`
- ATH 이후 최대 낙폭 `maxDrawdownPctSinceAth`
- DD 구간 `ddBucket`
- 전략 단계 `phase`
- 목표 비중 `targetWeights`
- 전략 활성화 여부 `strategyOn`
- 전략 버전 `version`

초기 상태가 없으면 최근 1년 QQQ 종가 데이터에서 ATH를 계산해 초기 상태를 생성한다.

### 3.3 DD 구간 정의

| 구간 | 조건 |
| :--- | :--- |
| `LESS_THAN_15` | DD < 15% |
| `FROM_15_TO_25` | 15% <= DD < 25% |
| `FROM_25_TO_35` | 25% <= DD < 35% |
| `FROM_35_TO_45` | 35% <= DD < 45% |
| `MORE_THAN_45` | DD >= 45% |

### 3.4 전략 단계 정의

- `NORMAL`: 해당 ATH 이후 최대 DD가 15% 미만인 상태
- `DRAWDOWN`: 최대 DD가 15% 이상이고 현재 DD가 10% 초과인 상태
- `RECOVERY`: 최대 DD가 15% 이상이지만 현재 DD가 10% 이하로 회복한 상태

추가 규칙:

- 전고점 돌파 시 ATH를 갱신하고 DD와 최대 DD를 0으로 리셋한다.
- 현재 DD가 10% 초과 15% 미만인 구간에서는 이전 목표 비중을 유지한다.

### 3.5 목표 비중

| 상태/구간 | QQQ | QLD | TQQQ |
| :--- | ---: | ---: | ---: |
| `NORMAL` 또는 DD < 15% | 100 | 0 | 0 |
| DD 15%~25% | 60 | 30 | 10 |
| DD 25%~35% | 40 | 40 | 20 |
| DD 35%~45% | 30 | 30 | 40 |
| DD 45% 이상 | 20 | 20 | 60 |
| `RECOVERY` | 70 | 30 | 0 |

## 4. 리스크 제어 규칙

### 4.1 실행 차단

다음 중 하나라도 만족하면 실제 주문 실행은 차단된다.

- `trading.execution.enabled = false`
- DB 기반 Kill Switch가 ON 상태

### 4.2 Circuit Breaker

보수적 운용을 위해 두 가지 필터를 사용한다.

- VIX 필터: `VIX >= 35`이면 레버리지 확대를 제한
- 200MA 필터: `QQQ 종가 < QQQ 200일 이동평균`이면 TQQQ 비중을 한 단계 낮춤

적용 순서:

1. 200MA 필터로 목표 비중을 한 단계 보수적으로 조정
2. VIX 필터로 이전보다 공격적인 레버리지 확대를 제한

## 5. 리밸런싱 판단 규칙

리밸런싱 판단은 `RebalanceDecisionService`가 수행한다.

### 5.1 판단 조건

- `strategyOn`이 `true`여야 한다.
- 총자산이 0보다 커야 한다.
- 실제 비중과 목표 비중 차이가 허용 오차를 넘는 종목이 하나 이상 있어야 한다.

현재 허용 오차 기본값:

- `trading.strategy.tolerance-pct = 5.0`

### 5.2 주문 방향과 우선순위

목표 비중보다 실제 비중이 높으면 매도, 낮으면 매수 인텐트를 생성한다.

우선순위는 설정값으로 관리되며 기본값은 다음과 같다.

- 매도: `TQQQ -> QLD -> QQQ`
- 매수: `QQQ -> QLD -> TQQQ`

## 6. 주문 생성 및 실행 규칙

### 6.1 주문 생성

`ExecutionJobCreateService`는 리밸런싱 결정을 실제 주문 단위로 변환한다.

- 기준 자산 총액과 목표 비중을 바탕으로 종목별 목표 금액을 계산한다.
- 실시간 가격을 기준으로 주문 수량을 계산한다.
- 수량이 0 이하이면 해당 주문은 생성하지 않는다.
- 같은 `signalDate`의 Job이 이미 있으면 중복 생성하지 않는다.

### 6.2 가격 정책

주문은 KIS 해외주식 주문을 기준으로 "체결 가능성을 높인 제한가 주문" 정책을 따른다.

현재 구현 메모:

- 현재 코드는 KIS 주문 구분을 지정가로 보내며, 주문 가격은 최근 체결가(last price)를 기준으로 산정한다.
- 이 과정에서 기본 버퍼 0.3%가 사용된다.
- 가격 정책 설정에는 매수 버퍼 0.5%, 매도 버퍼 0.5%, 수수료 0.25%가 정의되어 있으나, 현재 구현에서 실제 주문 가격 계산에 직접 반영되는 값은 기본 버퍼와 수수료다.

제품 정책 기준:

- 정규장 기본 주문가는 최근 체결가보다 현재 호가를 우선 기준으로 삼아야 한다.
- 매수는 현재 매도 호가(best ask), 매도는 현재 매수 호가(best bid)를 기준 가격으로 사용한다.
- 정규장 기본 버퍼는 0% 또는 최대 1~2틱 수준의 최소 보정만 허용한다.
- 고정 0.3% 버퍼를 기본 정책으로 사용해 불필요한 슬리피지 비용을 만들지 않는다.
- 수수료는 주문 가능 수량과 예상 체결 금액 계산에 별도로 반영한다.

매수는 사용 가능 현금 내에서만 수량을 산정한다.  
매도는 현재 보유 수량을 초과하지 않는다.

### 6.3 재시도 정책

`RetryableOrderExecutor`는 다음 규칙으로 재시도한다.

- 최대 3회 시도
- 정규장 기준 시도 간 체결 대기 시간은 2초로 둔다.
- 부분 체결 시 남은 수량만 재주문
- 미체결 수량은 취소 후 재시도
- 각 재시도 직전에는 현재 호가를 다시 조회해 기준 가격을 새로 잡는다.
- 최초 주문은 추가 버퍼 없이 현재 호가 기준으로 제출하는 것을 원칙으로 한다.
- 2차 시도는 재조회한 호가 기준으로 1틱만 추가 보정한다.
- 3차 시도는 재조회한 호가 기준으로 최대 2틱까지만 추가 보정한다.
- 재시도에서도 퍼센트 단위의 큰 고정 버퍼는 사용하지 않는다.

### 6.4 실행 상태

`ExecutionJob` 상태:

- `PENDING`
- `RUNNING`
- `COMPLETED`
- `FAILED`

`ExecutionOrder` 상태:

- `PLANNED`
- `REQUESTED`
- `ACCEPTED`
- `REJECTED`
- `CANCELED`
- `SKIPPED`

## 7. 운영 시나리오

### 7.1 EOD 계산

`StrategyEodScheduler`

- 실행 시간: 06:15 KST, 화요일~토요일
- 입력:
  - KIS에서 QQQ 전일 종가
  - Yahoo에서 VIX와 QQQ 200MA
- 결과:
  - 새로운 `StrategyState` 계산 및 저장

### 7.2 자동 리밸런싱

`RebalanceExecutionScheduler`

- 실행 시간: 23:45 KST, 월요일~금요일
- 전제:
  - 스케줄러 활성화
  - 실행 활성화
  - Kill Switch OFF
- 흐름:
  - 최신 전략 상태 조회
  - 현재 포트폴리오 조회
  - Circuit Breaker 데이터 조회
  - 리밸런싱 판단
  - Job 생성
  - 즉시 주문 실행

### 7.3 수동 운영 API

운영자는 다음 API를 통해 수동 개입할 수 있다.

- `POST /api/jobs/manual-rebalance`
- `POST /api/jobs/eod-calculation`
- `POST /api/jobs/{jobId}/execute`
- `GET /api/dashboard/summary`
- `GET /api/dashboard/history`

추가 KIS 운영 API:

- `GET /kis/token`
- `GET /kis/approval-key`
- `GET /kis/overseas-balance`
- `GET /kis/quoted-price`
- `GET /kis/realtime/overseas`
- `POST /kis/overseas/order/us/buy`
- `POST /kis/overseas/order/us/sell`

전역 필터가 적용되며 기본 정책은 다음과 같다.

  - `/api/dashboard/**`

- 공개 경로 제외
- IP 기준 초당 10 요청 허용

- 애플리케이션 로그와 에러 로그를 파일 롤링으로 기록
- Actuator `health`, `info`, `metrics` 노출

## 9. 현재 범위에 포함되지 않는 항목

다음은 코드 기준으로 아직 제품 범위에 포함되지 않는다.

- 별도 프론트엔드 애플리케이션
- 전략 파라미터의 웹 UI 편집
- 공개용 성과 페이지
- Slack/Email 알림
- NAV, 월별 PnL, MDD 중심의 성과 집계 스냅샷
- 실시간 체결/잔고 동기화 고도화
- JWT/2FA/OAuth 기반 자체 사용자 인증 체계

## 10. 문서 운영 원칙

- 이 문서는 현재 코드에서 역으로 도출한 기준 기획서다.
- Notion의 최신 기획서도 이 문서와 동일한 기준으로 유지한다.
- 과거 초안, 로드맵, 구현현황서는 참고용이 아니라 구버전 문서로 취급한다.
