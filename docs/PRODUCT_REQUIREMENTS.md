## 1. 문서 목적

이 문서는 QQQ 자동매매 시스템이 어떤 문제를 해결하려고 만들어졌는지, 어떤 사용자에게 어떤 가치를 제공하는지, 그리고 현재 제품 범위가 어디까지인지를 정의한다.

전략 수치와 세부 규칙은 이 문서에서 상세히 다루지 않는다. 전략 규칙은 `STRATEGY_SPEC.md`, 운영 절차는 `OPERATIONS_RUNBOOK.md`, 현재 구현과 목표 정책의 차이는 `CURRENT_IMPLEMENTATION_SYNC.md`를 기준으로 확인한다.

## 2. 문제 정의

미국 ETF 기반의 규칙형 운용은 다음과 같은 운영 문제를 가진다.

- 장 마감 후 전략 상태를 일관된 기준으로 계산해야 한다.
- 실제 보유 비중과 목표 비중을 사람이 반복적으로 비교하면 판단 누락과 지연이 발생한다.
- 주문 실행 과정을 수작업으로 수행하면 체결 추적, 재시도, 이력 관리가 분산된다.
- 전략 계산, 실행 차단, 수동 개입, 장애 대응의 기준이 문서화되지 않으면 운영 품질이 사람 숙련도에 의존하게 된다.

이 시스템은 위 문제를 줄이기 위해 QQQ 기반 상태 계산, 규칙형 리밸런싱 판단, 주문 실행 이력 관리, 운영용 조회/트리거 기능을 하나의 백엔드 애플리케이션으로 제공한다.

## 3. 제품 목표

현재 제품 목표는 다음과 같다.

- 전략 상태 계산을 일별 배치로 표준화한다.
- 리밸런싱 필요 여부를 명시적 규칙으로 판단한다.
- 주문 생성과 실행 과정을 추적 가능한 단위로 기록한다.
- 운영자가 수동 개입해야 하는 지점을 명확히 줄인다.
- 실거래 차단 조건과 비상 정지 수단을 제공해 운영 리스크를 낮춘다.

향후 필요하지만 아직 현재 범위에 충분히 포함되지 않은 목표는 다음과 같다.

- 성과 측정 체계의 표준화
- 운영 승인 체계의 고도화
- 보안과 권한 모델의 세분화

## 4. 운영 모델과 승인 원칙

현재 제품의 기본 운영 모델은 `사설망 전용`이다. 대시보드, 운영 API, Actuator는 로컬, 사설망, VPN, 또는 그에 준하는 내부 접근 경로를 기본 전제로 하며, 외부 인터넷 직접 노출은 기본 범위가 아니라 예외 운영 형태로 본다.

외부 노출이 필요한 경우에도 “조회 API는 공개 가능”을 기본 가정으로 두지 않는다. 별도 인증 계층, 리버스 프록시, 네트워크 제한 중 최소 하나 이상이 추가된 경우에만 예외적으로 허용하는 방향을 제품 원칙으로 둔다.

공개 읽기 API를 운영할 때는 reverse proxy 또는 CDN 뒤에 두고, 애플리케이션에는 신뢰 프록시 allowlist와 브라우저 origin allowlist를 함께 설정하는 것을 기본 원칙으로 둔다.
운영 환경에서는 샘플값을 코드에 남겨두지 않고 `TRADING_PUBLIC_READ_ALLOWED_ORIGINS`, `TRADING_PUBLIC_TRUSTED_PROXY_RANGES` 환경변수로 실제 값을 주입하는 것을 기본 원칙으로 둔다.

운영 모드는 아래 3단계를 공통 용어로 사용한다.

| 운영 모드 | 허용 범위 | 실주문 허용 여부 | 기본 의도 |
| :--- | :--- | :--- | :--- |
| `PAPER` | 계산, 판단, 이력 기록 | 금지 | 전략 검증과 운영 점검 |
| `MANUAL_LIVE` | 수동 트리거 기반 실행 | 수동 실주문만 허용 | 운영자 승인 하의 실거래 |
| `AUTO_LIVE` | 수동/자동 실행 모두 허용 | 허용 | 보호 장치 하의 자동 실거래 |

승인 원칙은 다음과 같다.

- `PAPER`는 `trading.execution.enabled` 값과 무관하게 실주문을 허용하지 않는다.
- `MANUAL_LIVE`는 운영자 수동 승인 기반 실행만 허용하고, 스케줄 기반 자동 실주문은 허용하지 않는다.
- `AUTO_LIVE`는 실행 플래그, Kill Switch, 데이터 정상성, 운영 캘린더 조건을 모두 통과한 경우에만 자동 실주문을 허용한다.
- 장애 복구 직후, 데이터 결측, 시장 일정 불확실성, 미정리 주문 존재 시에는 `AUTO_LIVE`를 유지하지 않고 `MANUAL_LIVE` 또는 `PAPER`로 낮춰 운영하는 것을 기본 원칙으로 한다.
- `AUTO_LIVE` 승격/강등은 정량 게이트 기반으로 관리하며, 최신 체크리스트와 예외 절차는 `docs/OPERATIONS_RUNBOOK.md`를 운영 기준 문서로 사용한다.

## 5. 핵심 사용자

### 운영자

이 제품의 핵심 사용자는 운영자다. 운영자는 전략 상태를 확인하고, 필요 시 EOD 계산이나 리밸런싱을 수동 트리거하며, 최근 작업 이력과 외부 연동 상태를 점검한다.

운영자 화면은 Admin Dashboard로 분리한다. Admin Dashboard는 내부 전용 화면이며 `/api/dashboard`, `/api/jobs`, `/api/operations`, `/kis`, `/actuator` 등 운영 API를 호출한다. 이 화면은 SSH tunnel, Tailscale, VPN, 또는 별도 인증 계층 뒤에서만 접근하는 것을 전제로 한다.

외부 공개 화면은 Public Dashboard로 분리한다. Public Dashboard는 인터넷 공개가 가능한 화면이며 `/public/api/v1/**`만 호출한다. 운영 API, 주문 이력, 운영 감사 이력, 실행 가드, 운영 모드는 Public Dashboard에 노출하지 않는다.

### 시스템

시스템은 운영자를 대체하는 독립 사용자라기보다, 운영자가 정의한 규칙을 일정한 스케줄과 제어 조건 아래 반복 수행하는 실행 주체다.

## 6. 사용자 가치와 주요 사용 시나리오

### 사용자 가치

- 전략 판단 기준이 상태 객체와 이력으로 남아 재현 가능성이 높아진다.
- 수동 계산과 주문 반복 작업이 줄어든다.
- Kill Switch와 실행 플래그를 통해 비정상 상황에서 즉시 차단할 수 있다.
- 대시보드를 통해 현재 포트폴리오, 전략 상태, 최근 작업 이력을 한곳에서 확인할 수 있다.

### 주요 사용 시나리오

1. 장 마감 후 시스템이 QQQ 종가 기준으로 전략 상태를 계산한다.
2. 미국장 개장 후 일정 시점에 시스템이 리밸런싱 필요 여부를 판단하고 실행을 시도한다.
3. 운영자는 필요 시 수동으로 EOD 계산 또는 리밸런싱을 실행한다.
4. 운영자는 대시보드와 작업 이력을 통해 현재 상태와 최근 실행 결과를 확인한다.
5. 운영자는 이상 징후가 있을 경우 실행을 차단하거나 수동 점검 절차로 전환한다.

## 7. 성공 기준

아래 KPI는 실측 데이터 축적 전의 `초기 운영 목표치(임시)`다. 초기 값은 운영 기준을 닫기 위한 출발점이며, 실측 축적과 사후 분석 결과에 따라 조정한다.
이 문서에서는 KPI 기준 초과 또는 위반 상황을 `KPI breach`로 부른다.

### KPI 집계 정의

- `EOD 계산 성공률`: 운영 캘린더상 EOD 계산 대상일 중, 최종 전략 상태 저장까지 성공한 일수의 비율이다. 휴장이나 정책상 skip한 일자는 분모에서 제외한다.
- `월간 수동 개입`: 정기 점검을 제외하고 운영자가 자동 흐름 밖에서 수동 실행, 재실행, 모드 전환, 주문 정리 판단을 수행한 횟수다. 단순 조회는 포함하지 않는다.
- `중복 Job 생성`: 동일 `signalDate`와 동일 목적의 Job이 중복 생성된 사례 수다. 동일 사고에서 여러 건이 발생해도 운영 이슈 단위로 1건 집계할 수 있다.
- `주문 실패율`: 전체 실주문 시도 건 중 재시도 종료 후에도 정상 체결 완료 또는 정상 종료로 정리되지 못한 건수의 비율이다.
- `미정리 주문`: 부분 체결, 취소 대기, 상태 불명 등으로 운영자가 후속 정리가 필요하다고 판단한 주문 또는 Job이다.
- `성과 데이터 누락`: 일별 NAV, 월별 손익, MDD 산출에 필요한 필수 데이터가 비어 있거나 신뢰할 수 없는 상태를 뜻한다.

### 운영 KPI

- EOD 계산 성공률 `>= 99%`
- 월간 수동 개입 `<= 2회` (정기 점검 제외)

운영 액션:

- EOD 계산 성공률이 기준을 벗어나거나 단일 EOD 실패가 발생하면 자동 실행을 중지하고 `MANUAL_LIVE` 이하로 운영한다.
- 월간 수동 개입이 반복적으로 기준을 초과하면 `AUTO_LIVE` 유지 근거를 재검토하고 원인 분석을 수행한다.

### 안전 KPI

- 중복 Job 생성 `0건`
- Kill Switch 활성 중 실주문 `0건`
- 데이터 결측 또는 브로커 장애 상태에서 `AUTO_LIVE` 실주문 `0건`

운영 액션:

- 중복 Job 정황이 발견되면 즉시 자동 실행을 중지하고 동일 `signalDate` 기준 이력을 점검한다.
- Kill Switch 활성 중 실주문이 발생하면 `AUTO_LIVE`를 즉시 해제하고 실행 가드 전체를 재점검한다.
- 데이터 결측 또는 브로커 장애 상태의 실주문이 확인되면 `PAPER`까지 강등하는 것을 기본 대응으로 한다.

### 체결 KPI

- 주문 실패율 `<= 5%`
- 재시도 후에도 미정리 주문으로 남는 건은 운영 이슈로 관리하고, 정상 운영 상태에서는 누적 방치를 허용하지 않는다.

운영 액션:

- 주문 실패율이 `5%`를 초과하면 `AUTO_LIVE -> MANUAL_LIVE` 강등을 우선 검토하고, 반복 시 즉시 강등한다.
- 재시도 후 미정리 주문이 누적되면 자동 실행을 중지하고 수동 정리 후에만 재개를 검토한다.

### 성과 KPI

- 초기 단계에서는 수익률 목표보다 측정 체계 확보를 우선한다.
- 일별 NAV, 월별 손익, MDD 산출에 필요한 기준 데이터 누락 `0건`
- 전략 수익률과 MDD 목표치는 실측 데이터가 누적되기 전까지 확정하지 않고, 측정 체계 구축 후 별도 성과 기준으로 보정한다.

운영 액션:

- NAV, 월별 손익, MDD 산출 데이터가 누락되면 성과 해석을 중단하고 `AUTO_LIVE` 유지 여부를 재검토한다.
- 성과 KPI는 승격 조건의 직접 입력값이 아니라 사후 분석과 파라미터 재검토의 필수 입력값으로 관리한다.

## 8. 현재 범위

현재 제품 범위에 포함되는 기능은 다음과 같다.

- QQQ 종가 기준 전략 상태 계산
- 목표 비중과 실제 비중 차이에 따른 리밸런싱 판단
- 주문 단위 생성과 실행 이력 관리
- 자동 스케줄 기반 EOD 계산과 리밸런싱 실행
- 운영자용 수동 실행 API
- 대시보드 요약 및 작업 이력 조회
- 공개 포트폴리오 요약 및 성과 읽기 API
- 실행 차단 플래그와 Kill Switch 기반 보호 장치
- 기본 API Key 인증과 레이트 리밋

## 9. 다음 범위

현재 범위는 아니지만 운영 완성도를 위해 다음 단계에서 우선 검토할 범위는 아래와 같다.

- Admin Dashboard 수동 실행 flow
  - 실행 전 점검
  - 주문 미리보기
  - 최종 확인
  - 실행 후 Job/Order 확인
- Public Dashboard 별도 프론트 페이지
- 성과 측정 체계와 운영 해석 기준 고도화
- 운영 API, 대시보드, Actuator를 프록시/VPN/추가 인증 뒤에 두는 실제 인프라 구성

## 10. 현재 비범위

다음 항목은 현재 범위에 포함되지 않는다.

- 별도 프론트엔드 애플리케이션
- 전략 파라미터의 웹 UI 편집
- 절대 금액 기반 공개 페이지
- 실시간 체결/잔고 동기화 고도화
- JWT, 2FA, OAuth 기반 사용자 인증 체계
- curl 직접 호출을 표준 수동 실주문 절차로 사용하는 운영 방식

공개 범위 원칙:

- 외부 공개 API는 운영 대시보드와 분리된 읽기 모델로 관리한다.
- 공개 데이터는 EOD 스냅샷 기준의 비율 정보만 노출한다.
- 공개 응답에는 절대 NAV, 현금 금액, 주문/운영 감사 이력, 실행 가드, 운영 모드를 포함하지 않는다.
- Public Dashboard는 별도 외부 프론트가 `/public/api/v1/**`만 소비하는 것을 전제로 한다.

## 11. 주요 리스크와 제약

현재 제품은 아래 제약을 전제로 운영된다.

- 단일 브로커(KIS) API와 외부 시세 소스에 의존한다.
- Yahoo 기반 보조 지표가 결측이거나 지연될 수 있다.
- 레버리지 ETF 운용 특성상 변동성 확대 구간에서 손실 폭이 커질 수 있다.
- 환율, 세금, 장기 보유 비용은 전략 성과 해석에 영향을 주지만, 현재 문서와 구현에는 제한적으로만 반영돼 있다.
- 전략 파라미터의 정량 검증과 성과 측정 체계가 아직 충분히 문서화되지 않았다.
- 대시보드와 운영 API는 단일 운영자 중심 설계이며 역할 분리 모델이 없다.
- 사설망 전용이 기본 운영 모델이므로, 외부 노출 환경에서는 추가 보안 계층 없이는 제품 기준을 충족하지 못한다.
- 실행 리스크 한도가 문서와 시스템에 충분히 연결되지 않으면 자동 실거래 안정성이 저하될 수 있다.
