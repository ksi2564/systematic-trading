# 003. 저비용 단일 클라우드 배포 기준

## Status
Accepted

## Context
현재 프로젝트는 단일 사용자용 자동매매 시스템이며, 운영 모드도 아직 `PAPER -> MANUAL_LIVE -> AUTO_LIVE` 순으로 보수적으로 올려야 한다.

외부에 공개할 범위는 공개 포트폴리오 읽기 API 정도로 제한적이고, 운영 API와 대시보드는 내부 접근이 전제다. 이 조건에서 관리형 인프라나 다중 서버 구성을 먼저 도입하면 비용과 운영 복잡도가 기능 성숙도보다 앞서게 된다.

## Decisions

### 1. 운영 백엔드는 단일 VM 1대에 둔다
- 애플리케이션, MySQL, 스케줄러를 같은 Ubuntu VM에서 운영한다.
- 초기 기준은 `AWS Lightsail 2GB` 급 단일 VM이다.
- `PAPER` 운영 안정화 전에는 다중 서버, 관리형 DB, 로드밸런서를 도입하지 않는다.

### 2. 공개 경계는 reverse proxy가 담당한다
- Spring Boot는 `127.0.0.1:8080`, MySQL은 `127.0.0.1:3306`에만 바인딩한다.
- `Caddy` 또는 동급 reverse proxy가 `80/443`에서 TLS 종료 후 `/public/api/v1/**`만 외부로 전달한다.
- `/api/dashboard/**`, `/api/jobs/**`, `/api/operations/**`, `/kis/**`, `/actuator/**`는 퍼블릭 DNS에 매핑하지 않는다.

### 3. 운영 접근은 SSH 터널을 기본으로 한다
- 운영 API는 VPN이나 별도 운영 프런트보다 `SSH tunnel`을 기본 운영 경로로 삼는다.
- 혼자 쓰는 시스템이라는 조건에서 가장 싼 비용으로 내부 API를 보호하는 방식이다.

### 4. 맥미니는 런타임 경로가 아니라 백업/복구 경로로 쓴다
- 집 맥미니는 운영 본체가 아니다.
- 역할은 오프사이트 백업 저장소, 복구 리허설 환경, 비상용 관리 머신으로 제한한다.

## Consequences

- **Positive**: 월 고정비를 낮게 유지하면서 현재 구현의 운영 경계와 잘 맞는다.
- **Positive**: 배포 토폴로지가 단순해 장애 위치를 파악하기 쉽다.
- **Negative**: 단일 VM 장애 시 자동 복구 범위가 제한적이고 무중단은 보장하지 않는다.
- **Negative**: MySQL과 애플리케이션이 같은 노드에 있어 자원 경합이 생길 수 있다.
- **Negative**: 공개 API와 운영 API를 모두 앱 안에 두되, 경계 enforcement를 인프라에 강하게 의존한다.
