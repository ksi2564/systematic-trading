# v2 단계적 전환과 롤백

## 1. 전환 원칙

- Java를 멈추기 전에 Python v2가 자동 섀도로 충분히 증명되어야 한다.
- Java와 v2가 같은 계좌에 동시에 주문을 보낼 수 있는 순간을 만들지 않는다.
- 접근 경로 배포, 섀도 완료, LIVE 전환을 별도 승인으로 다룬다.
- 불명확한 주문이 있으면 자동 복귀나 재전송보다 정지와 확인을 우선한다.
- LIVE 주문, Java 중단, DNS·트래픽 전환, 공유 staging/운영 롤백 확정은 모두 사용자
  승인 필수다. 로컬·일회용 복사본의 복구 훈련만 승인 범위 안에서 자동화할 수 있다.

## 4. C1: 접근 QA

자동으로 확인할 수 있는 항목:

- 미인증 접근은 로그인으로 이동하거나 거부됨
- 허용된 기존 세션에서 UI와 동일 출처 API가 열림
- 원본 API 무인증 `401`
- v2 화면·API의 execution false, broker disabled
- Java와 v2 서비스가 함께 active이며 포트가 분리됨

사용자 승인 없이는 Access 허용 목록, Published application route, DNS, Caddy의 기존 Java
경로를 바꾸지 않는다. OTP가 필요하면 입력 단계만 사용자에게 남긴다.

## 5. C2~C3: 안전 섀도

C2·C3의 개발·테스트·관찰은 C0 범위 승인 이후에만 시작하며, 승인된
전략·시점·스테이징 생성 범위 안에서 자동 진행할 수 있다.

### 시작 체크

- [ ] 승인된 QQQM 기준선 checksum 고정
- [ ] 16:15 ET `EOD_STATE`와 다음 거래일 09:45 ET `REBALANCE_INTENT`가 별도
      실행·멱등키·입력 시각으로 고정
- [ ] 공식 데이터·계좌 조회 어댑터가 주문 API와 분리됨
- [ ] `WALLANT_EXECUTION_ENABLED=false`
- [ ] `WALLANT_BROKER_ADAPTER=disabled`
- [ ] Java 서비스·스케줄·DB 변경 없음
- [ ] 섀도 DB 백업·보존 위치 확인
- [ ] 화면에 마지막 성공·차이·차단 이유 표시

## 6. C4: 전환 리허설

실제 주문 없이 다음을 연습한다.

1. v2 섀도 스케줄을 정지한다.
2. 실행 플래그·브로커 disabled를 재확인한다.
3. DB 백업을 만들고 무결성을 검사한다.
4. 직전 v2 릴리스 심볼릭 링크로 되돌린다.
5. API·웹·감사·데이터를 확인한다.
6. Java가 계속 active이고 바뀌지 않았음을 확인한다.
7. 소요 시간, 담당자, 실패 지점을 증적에 남긴다.
8. 격리된 durable journal·broker simulator에서 제출 직전부터 체결 반영 뒤까지 각
   crash point를 재현하고, 재기동 후 주문·감사 상태 누락과 중복이 0인지 확인한다.

스키마 마이그레이션은 릴리스 링크 롤백으로 되돌아가지 않는다. 호환되지 않는 변경은
배포 전에 백업 복원 리허설과 forward-fix 계획이 모두 필요하다.

배포 스크립트는 호스트의 `/run/lock/wallant-v2-deploy.lock` 비차단 잠금을 먼저
획득하므로 Actions 밖의 직접 실행을 포함해 동시에 두 배포가 current·rollback·retention을
바꿀 수 없다. 정상 종료와 오류 trap은 잠금 디렉터리를 해제한다. 강제 종료 뒤 잠금이
남으면 다음 배포는 자동 삭제나 PID 추정 없이 실패하고, 운영자가 실행 중 프로세스가
없음을 확인한 뒤에만 정확한 잠금 디렉터리를 수동 정리한다. 릴리스 경로는
`SHA.UTC시각.PID` 단위로 불변이다. 실패 trap은 현재 attempt의 `.incoming`을 정리하되,
이전 서비스의 재시작·health 검증까지 성공한 `ROLLBACK_STATUS=verified`일 때만 실패
release를 지운다. rollback 자체가 검증되지 않으면 실행 중인 프로세스가 새 release의
바이트를 참조할 수 있으므로 `FAILED_RELEASE_PRESERVED`로 보존하고 수동 확인을 요구한다.
성공 뒤에는 현재 release, 직전 rollback 대상,
최신 완료 attempt 3개(중복 제외)를 보존하고 나머지 관리 대상만 정리한다. 정리에
실패하면 서비스 성공을 되돌리지 않고 `RELEASE_RETENTION=warning`을 출력해 수동
확인을 요구한다. host lock owner/rmdir 정리에 실패하면 성공 exit를 유지하지 않고
workflow를 실패시켜 다음 배포가 잠금 잔존을 놓치지 않게 한다. 이 보존 정책은 배포
실행 권한이나 공유 환경 변경 승인을 대신하지 않는다.

서비스 전환 전 `/etc/wallant/v2.env`의 주문 안전 키는 단순 포함 여부가 아니라 strict
parser로 확인한다. `WALLANT_EXECUTION_ENABLED=false`와
`WALLANT_BROKER_ADAPTER=disabled`가 공백 변형 없이 각각 정확히 한 번만 있어야 하며,
중복·누락·다른 값·systemd가 같은 키로 해석할 앞/뒤 공백 변형은 current 링크나 서비스를
바꾸기 전에 배포를 중단한다. Access 설정 변경도 같은 검사를 변경 전후에 수행한다.

배포 프로세스가 HUP·INT·TERM을 받으면 미검증 current를 남기지 않고 일반 오류와 같은
rollback을 먼저 수행한 뒤 EXIT 단계에서 host lock을 해제한다. SIGKILL처럼 trap을
실행할 수 없는 종료는 잠금이 남아 다음 실행을 막으므로 수동 확인 없이 자동 재개하지
않는다. rollback 경로 자체는 `set -e` 조기 중단을 끄고 링크·unit·restart를 모두 시도한
뒤 이전 release 경로의 SHA prefix·`release.env` SHA·health SHA와 health
UP·execution false·broker disabled가 모두 일치할 때만
`ROLLBACK_STATUS=verified`를 출력한다. #54처럼 `release.env`가 없고 release 경로가
정확한 40자 SHA인 legacy 형식은 이전 unit을 복구·재시작한 뒤 health UP·execution
false·broker disabled까지 확인하고 `verified-legacy`로 구분한다. 이 경우 health의
build SHA 증명은 불가능하다는 사실을 함께 남긴다. 하나라도 확인하지 못하면 `failed`로
남기고 새 release를 보존해 복구 완료를 단정하지 않는다. 최초 배포 rollback도 stop과
`is-active=inactive`(정상적인 exit 3), `MainPID=0`이 모두 확인된 뒤에만 current 링크와
실패 release를 제거한다. D-Bus·systemd 상태 조회 오류는 inactive로 해석하지 않는다.

`deploy_staging_fault_injection_test.sh`는 운영 서버와 분리된 임시 경로에서 배포 스크립트
전체 제어 흐름을 실행한다. modern·legacy·same-SHA 성공/복구, health transport·안전값·SHA
오류, 안전 키 중복 충돌의 pre-switch 거부, 기존 비정상 서비스 stop 실패의 pre-switch
거부, rollback 경로/SHA 불일치, systemd restart 오류, HUP·TERM, rollback health/restart
실패, 최초 배포 stop 성공/실패·상태 조회 오류, active/stale/cleanup-failed lock을 상태형
fake systemd·runtime SHA로 검증한다.
실제 staging의 systemd·DB·health 장애 훈련은 공유 환경 변경 승인을 받은 뒤 별도 증적으로
남긴다.

workflow의 원격 script·archive 임시 경로에는 GitHub run ID와 run attempt가 모두 들어가
재시도 cleanup이 다른 실행의 파일을 지우지 않는다. 배포 스크립트가 잠금을 놓은 뒤에도
workflow가 current 링크·`release.env`·health의 전체 SHA와 execution false·broker
disabled를 다시 확인해야 성공한다. 배포 전에는 기존 `trading.service`가 active이고
MainPID가 0이 아님을 요구하며, 배포 직후에도 동일 PID·active를 강제해 기존
QQQM/QLD/TQQQ 운용 프로세스의 중단이나 재시작을 성공으로 오인하지 않는다.

자동 실행 범위는 로컬·일회용 DB와 릴리스 복사본에 한한다. 공유 staging이나 운영에서
스케줄 중지, 서비스 재시작, 심볼릭 링크 교체, DB backup/restore, Java·DNS 변경을
하려면 대상·명령·기대 영향·되돌릴 값을 보여 주고 실행 직전 사용자 승인을 받는다.

RTO/RPO는 C0 D-09의 승인값으로 통과 판정한다. 현재 제안값은 섀도 RTO 30분/
RPO 1 미국 거래일, canary·LIVE RTO 15분, 주문·감사 RPO 0이며 실제 리허설 전에는
단지 목표다.

## 7. C5: LIVE canary — 사용자 실행 승인 전용

canary 계획서에 아래 값이 빈칸 없이 있어야 한다.

- 대상 계좌·전략 checksum
- 허용 종목: QQQM, QLD, TQQQ
- 1회/1일 금액, 주문 수, 최대 손실
- 시작·종료 시각, 자동 연장 가능한 최대 종료일과 담당자
- Java 주문 소유권을 끄는 정확한 절차
- v2 주문 소유권을 켜는 정확한 절차
- 첫 주문 전 읽기 전용 잔고·미체결 확인
- 접수 불명 시 재전송 금지와 브로커 확인 절차
- 즉시 중단 기준과 복귀 절차

실행은 서로 다른 두 게이트로 나눈다. 둘 다 현재 작업에서 실행하지 않으며, 각 단계
직전에 계좌·금액·기간을 다시 보여 주고 사용자 승인을 받는다.

### C5-A. 단건 제출 안전 canary

1. v2 신규 스케줄을 정지하고 Java·v2 미확정 주문이 0인지 확인한다.
2. 사용자 승인 후 Java 자동 주문 소유권을 끄고 제출 불가를 확인한다. Java 서비스는
   warm/read-only로 둘 수 있다.
3. 제한된 v2 LIVE 게이트를 열고 첫 판단·의도·정확한 종목·수량·최대 금액을 보여 준다.
4. 사용자가 **v2의 단건 제출**을 별도 승인한 경우에만 한 번 제출한다.
5. 접수 ID, 미체결·부분체결, 체결·현금·잔고·전략 상태를 대조한 뒤 gate를 닫는다.
6. 미확정 주문 0건을 확인한 같은 운영 세션에서 사용자가 `C5-B 즉시 진입` 또는
   `Java 주문 소유권 복원` 중 하나를 확정한다. 이 종료 결정을 받을 수 없으면 C5-A를
   시작하지 않는다.

사용자가 브로커 화면에서 직접 낸 주문은 운영 절차 점검에는 쓸 수 있지만 v2 제출
adapter의 인수 증적으로 세지 않는다. C5-A만으로 `V2-LIV-001`을 완료하지 않는다.

### C5-B. 예약 자동운용 canary

1. C5-A가 통과하고 미확정 주문 0건을 다시 확인한다.
2. 사용자가 제한 계좌·전략·금액·기간과 스케줄 활성화를 별도 승인한다.
3. Java는 주문 소유권이 없는 warm/read-only 상태로 유지하고, v2에만 제한된 주문
   소유권과 16:15/09:45 스케줄을 연다.
4. **연속 미국 거래일 5개 EOD→다음 거래일 09:45 주기**를 자동 완주하고, 자연 발생한
   v2 자동 제출·접수·체결 대조를 최소 1회 확인한다. 주문 의도가 없으면 승인된 최대
   종료일까지 연장할 수 있지만 거래를 만들기 위해 전략이나 입력을 바꾸지 않는다.
   최대 종료일 이후 연장은 계좌·금액·새 종료일을 다시 보여 주고 별도 승인받는다.
5. 각 주기마다 소유권, 접수, 미체결·부분체결, 현금·잔고·전략 상태, 감사·알림을
   대조한다. D-10 중단 조건이면 남은 제출을 차단하고 사용자 판단을 기다린다.
6. canary 종료 후 C6 진행 또는 Java 복귀는 현재 상태와 미확정 주문 0건을 보여 주고
   사용자가 별도로 확정한다.

DNS·트래픽 전환은 주문 소유권과 별개 변경으로 취급하며 별도 사용자 승인이 필요하다.

## 8. 롤백 트리거

다음 중 하나면 v2 신규 제출을 즉시 차단한다.

- 전략 상태·목표 비중의 중대 불일치
- 공식 입력 누락·기준일 혼합·지연 데이터 사용
- 중복 또는 멱등키 충돌 주문
- 주문 접수 여부 불명
- 계좌·잔고·체결 reconciliation 불일치
- 실행 한도 초과 또는 손실 한도 도달
- 화면 안전 상태와 서버 설정 불일치
- 인증 우회, 비밀값 노출, 감사 기록 누락

이미 승인된 fail-closed 게이트가 실행 중이라면 서버 내부 submission freeze로 v2 신규
제출 차단을 자동 설정·유지하고, 접수 불명 등 D-10 중단 조건의 영향 계좌는 보호 정지한다.
이는 Java·브로커 주문·DNS·서비스를 바꾸지 않는다. freeze 해제, 계좌·전역 재개, 자동
취소·재전송, 공유 staging/운영 서비스 변경, 롤백 확정과 Java 복귀는 실행 직전 사용자
승인을 기다린다.

## 9. 롤백 순서

```text
v2 신규 제출 차단
        ↓
미확정·부분체결 주문 확인 ── 불명확 ─→ 계좌 정지 유지 + 사용자/브로커 확인
        ↓ 명확
잔고·현금·전략 상태 스냅샷 저장
        ↓
v2 앱/스키마 복구 판단
        ↓
Java readiness 확인
        ↓
사용자 롤백 확정
        ↓
Java에 단일 주문 소유권 복원
        ↓
첫 자동 판단 전 dry preview와 감사 기록
```

세부 절차:

1. v2 전역·계좌 정지와 제출 게이트 차단을 확인한다.
2. 취소·재전송하지 말고 브로커 조회로 모든 주문 상태를 확정한다.
3. 체결 반영 뒤 잔고·현금·당일 위험 사용량을 저장한다.
4. 애플리케이션 결함이면 직전 릴리스로 링크를 복구한다.
5. 스키마 결함이면 사전 계획에 따라 백업 복원 또는 forward-fix를 선택한다.
6. Java의 코드·설정·DB·스케줄 readiness를 읽기 전용으로 확인한다.
7. 사용자에게 현재 상태, 미확정 항목, 예상 영향을 보여 주고 롤백 확정을 받는다.
8. Java만 주문 소유권을 갖도록 복원한다.
9. 첫 실행 전 목표 비중·주문 preview를 검토하고 재개한다.
10. 장애 타임라인, 주문·체결, 데이터 checksum, 승인자를 보존한다.

## 11. 전환 완료 정의

전환 완료는 다음이 모두 참일 때만 선언한다.

- v2가 승인한 계좌의 유일한 주문 소유권을 가진다.
- Java 자동 주문 경로가 사용자 승인과 증적을 갖고 중단됐다.
- 16:15 상태 저장과 다음 미국 거래일 09:45 판단이 자동으로 이어지고, 제출 요청은
  멱등한 1회로 접수 ID를 확인하며 미체결·부분체결을 추적한다.
- 체결·현금·잔고·전략 상태가 대조되고 접수 불명시 자동 재전송하지 않는다.
- 미확정 주문과 잔고 차이가 없다.
- 화면·감사·알림·백업·복구가 운영 기준을 통과했다.
- C6 뒤 연속 미국 거래일 20일 안정화 동안 롤백 트리거가 없었다.
- DNS·트래픽 상태가 승인한 구성과 일치한다.

현재 상태는 이 정의를 충족하지 않는다. C1 접근 기반과 안전한 연구 화면은 마지막
제어된 실행에서 확인했지만 현재 원격 런타임은 재확인하지 못했다. C2 이후는
개발·검증 대상이다.
