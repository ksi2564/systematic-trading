# v2 단계적 전환과 롤백

## 1. 전환 원칙

- Java를 멈추기 전에 Python v2가 자동 섀도로 충분히 증명되어야 한다.
- Java와 v2가 같은 계좌에 동시에 주문을 보낼 수 있는 순간을 만들지 않는다.
- 접근 경로 배포, 섀도 완료, LIVE 전환을 별도 승인으로 다룬다.
- 불명확한 주문이 있으면 자동 복귀나 재전송보다 정지와 확인을 우선한다.
- LIVE 주문, Java 중단, DNS·트래픽 전환, 롤백 확정은 모두 사용자 승인 필수다.

| 단계 | 목적 | 진입 조건 | 종료 조건 | 권한 |
| --- | --- | --- | --- | --- |

| `C6 전체 전환` | v2를 유일 주문 주체로 지정 | canary 통과·최종 승인 | 안정화 기간 통과 | 사용자 승인 필수 |
| `C7 Java 퇴역` | 운영 복잡도 제거 | 장기 안정화·백업 확인 | 복구용 보존 정책 실행 | 사용자 승인 필수 |

## 4. C1: 접근 QA

자동으로 확인할 수 있는 항목:

- 미인증 접근은 로그인으로 이동하거나 거부됨
- 허용된 기존 세션에서 UI와 동일 출처 API가 열림
- 원본 API 무인증 `401`
- v2 화면·API의 execution false, broker disabled
- Java와 v2 서비스가 함께 active이며 포트가 분리됨

사용자 승인 없이는 Access 허용 목록, Published application route, DNS, Caddy의 기존 Java
경로를 바꾸지 않는다. OTP가 필요하면 입력 단계만 사용자에게 남긴다.

## 5. C2~C3: 안전 섀도

C2·C3의 개발·테스트·관찰은 C0 범위 승인 이후에만 시작하며, 승인된
전략·시점·스테이징 생성 범위 안에서 자동 진행할 수 있다.

### 시작 체크

- [ ] 승인된 QQQM 기준선 checksum 고정
- [ ] 16:15 ET `EOD_STATE`와 다음 거래일 09:45 ET `REBALANCE_INTENT`가 별도
      실행·멱등키·입력 시각으로 고정
- [ ] 공식 데이터·계좌 조회 어댑터가 주문 API와 분리됨
- [ ] `WALLANT_EXECUTION_ENABLED=false`
- [ ] `WALLANT_BROKER_ADAPTER=disabled`
- [ ] Java 서비스·스케줄·DB 변경 없음
- [ ] 섀도 DB 백업·보존 위치 확인
- [ ] 화면에 마지막 성공·차이·차단 이유 표시

### 권장 20거래일 통과 기준

| 지표 | 기준 |
| --- | ---: |
| 예정된 16:15/09:45 섀도 실행 | 각각 100% 완료 또는 설명된 휴장·입력 차단 |
| 중대 전략 차이 | 0건 |
| 설명되지 않은 주문 의도 차이 | 0건 |
| 입력 차단 미해결 | 0건 |
| 중복 결과·중복 주문 의도 | 0건 |
| 실제 브로커 제출 호출 | 0건 |
| Java 운영 영향 | 0건 |

중대 차이가 생기면 수정한 버전의 checksum을 새로 고정하고 관찰 기간을 처음부터 다시
센다. 차이를 단순 무시하는 예외는 사용자 승인과 이유가 있어야 한다.

## 6. C4: 전환 리허설

실제 주문 없이 다음을 연습한다.

1. v2 섀도 스케줄을 정지한다.
2. 실행 플래그·브로커 disabled를 재확인한다.
3. DB 백업을 만들고 무결성을 검사한다.
4. 직전 v2 릴리스 심볼릭 링크로 되돌린다.
5. API·웹·감사·데이터를 확인한다.
6. Java가 계속 active이고 바뀌지 않았음을 확인한다.
7. 소요 시간, 담당자, 실패 지점을 증적에 남긴다.

스키마 마이그레이션은 릴리스 링크 롤백으로 되돌아가지 않는다. 호환되지 않는 변경은
배포 전에 백업 복원 리허설과 forward-fix 계획이 모두 필요하다.

## 7. C5: LIVE canary — 사용자 수동 전용

canary 계획서에 아래 값이 빈칸 없이 있어야 한다.

- 대상 계좌·전략 checksum
- 허용 종목: QQQM, QLD, TQQQ
- 1회/1일 금액, 주문 수, 최대 손실
- 시작·종료 시각과 담당자
- Java 주문 소유권을 끄는 정확한 절차
- v2 주문 소유권을 켜는 정확한 절차
- 첫 주문 전 읽기 전용 잔고·미체결 확인
- 접수 불명 시 재전송 금지와 브로커 확인 절차
- 즉시 중단 기준과 복귀 절차

실행 순서:

1. 신규 스케줄을 모두 정지한다.
2. Java·v2의 미확정 주문이 0인지 확인한다.
3. 사용자 승인 후 Java 자동 주문 소유권을 끈다.
4. Java가 제출하지 못함을 확인한다. 서비스 자체는 warm/read-only로 둘 수 있다.
5. 사용자 승인 후 제한된 v2 LIVE 게이트를 연다.
6. 첫 판단과 주문 의도를 화면에서 확인한다.
7. 실제 주문 제출은 사용자가 직접 수행하거나 별도 명시 승인 후에만 수행한다.
8. 체결·잔고·상태를 대조하고 canary를 종료한다.

DNS·트래픽 전환은 주문 소유권과 별개 변경으로 취급하며 별도 사용자 승인이 필요하다.

## 8. 롤백 트리거

다음 중 하나면 v2 신규 제출을 즉시 차단한다.

- 전략 상태·목표 비중의 중대 불일치
- 공식 입력 누락·기준일 혼합·지연 데이터 사용
- 중복 또는 멱등키 충돌 주문
- 주문 접수 여부 불명
- 계좌·잔고·체결 reconciliation 불일치
- 실행 한도 초과 또는 손실 한도 도달
- 화면 안전 상태와 서버 설정 불일치
- 인증 우회, 비밀값 노출, 감사 기록 누락

자동으로 가능한 첫 조치는 v2 `execution=false`, broker disabled, 계좌/전체 pause다. 실제
롤백 확정과 Java 복귀는 사용자 승인을 기다린다.

## 9. 롤백 순서

```text
v2 신규 제출 차단
        ↓
미확정·부분체결 주문 확인 ── 불명확 ─→ 계좌 정지 유지 + 사용자/브로커 확인
        ↓ 명확
잔고·현금·전략 상태 스냅샷 저장
        ↓
v2 앱/스키마 복구 판단
        ↓
Java readiness 확인
        ↓
사용자 롤백 확정
        ↓
Java에 단일 주문 소유권 복원
        ↓
첫 자동 판단 전 dry preview와 감사 기록
```

세부 절차:

1. v2 전역·계좌 정지와 제출 게이트 차단을 확인한다.
2. 취소·재전송하지 말고 브로커 조회로 모든 주문 상태를 확정한다.
3. 체결 반영 뒤 잔고·현금·당일 위험 사용량을 저장한다.
4. 애플리케이션 결함이면 직전 릴리스로 링크를 복구한다.
5. 스키마 결함이면 사전 계획에 따라 백업 복원 또는 forward-fix를 선택한다.
6. Java의 코드·설정·DB·스케줄 readiness를 읽기 전용으로 확인한다.
7. 사용자에게 현재 상태, 미확정 항목, 예상 영향을 보여 주고 롤백 확정을 받는다.
8. Java만 주문 소유권을 갖도록 복원한다.
9. 첫 실행 전 목표 비중·주문 preview를 검토하고 재개한다.
10. 장애 타임라인, 주문·체결, 데이터 checksum, 승인자를 보존한다.

| C2~C3 섀도 | 스케줄 정지, 직전 릴리스 복구, 데이터 보존 | 없음 | C0 범위 승인 이후 자동 진행 가능 |

## 11. 전환 완료 정의

전환 완료는 다음이 모두 참일 때만 선언한다.

- v2가 승인한 계좌의 유일한 주문 소유권을 가진다.
- Java 자동 주문 경로가 사용자 승인과 증적을 갖고 중단됐다.
- 미확정 주문과 잔고 차이가 없다.
- 화면·감사·알림·백업·복구가 운영 기준을 통과했다.
- 안정화 기간 동안 롤백 트리거가 없었다.
- DNS·트래픽 상태가 승인한 구성과 일치한다.

현재 상태는 이 정의를 충족하지 않는다. 현재는 C1 접근 기반과 안전한 연구 화면이
배포된 상태이며 C2 이후는 개발·검증 대상이다.
